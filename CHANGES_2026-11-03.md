## 1. New Bluetooth & Zigbee page (receive-only)

A new workspace page lists Bluetooth LE advertisers and IEEE 802.15.4 / Zigbee
nodes. They are decoded from the 2.4 GHz captures the receiver already takes,
without retuning or transmitting. The page is off until **Start Bluetooth &
Zigbee decoding** is pressed.

| Part | What it does |
|---|---|
| Bluetooth LE decoder | Decodes legacy and extended advertising (LE 1M) on channels 37/38/39 with CRC check. Parses every advertising field, with company and service names. Recognises Apple, Google, Microsoft, Eddystone and Remote ID formats. |
| Zigbee / 802.15.4 decoder | Decodes channels 11–26 with FCS check. Parses MAC addresses, beacons, MAC commands and Zigbee network headers, and recognises 6LoWPAN/Thread. Encrypted payloads are not decrypted. |
| Background service | Runs at nice 10 with a bounded 4-capture / 768 MiB queue; captures beyond it are dropped and counted. Records per-channel coverage. Keeps 2,048 Bluetooth and 256 Zigbee addresses, plus recent packets. Exports JSON to `data/shortrange/`. |
| Page | Bluetooth list on the left and Zigbee list on the right, with search and a details panel. Also coverage, recent packets, export, and mode warnings. |
| Drones page | New "Bluetooth Remote ID" section, parsed with the existing Remote ID parser. |

### List behaviour (later requests)

- **Stable rows.** Named Bluetooth devices come first, then first-seen order; Zigbee shows known vendors first. Rows don't move as packets arrive; only counts change. Power and last-seen start as hidden columns.
- **Extendable tables.** A drag handle sets each table's height. Columns can be resized, reordered and hidden (right-click a header).
- **Rotating addresses merged.** "Merge rotating addresses" is on by default and is a provisional heuristic. It joins addresses with the same advert layout and timing whose median carrier offset is within 3 kHz and power within 12 dB, only when one candidate is clearly best. The link breaks if the old address is heard again.
  - A merged row keeps its place and shows "(+N)"; the details panel lists the chain and the evidence.
  - "Hide if not heard for 2/10/30 min" hides quiet rows instead.

## 2. Receiver centre-frequency fix (affects existing features)

UHD's RX tune result centres the samples at `actual_rf − actual_dsp`, which is
what `get_rx_freq()` returns on the X310. The code used `actual_rf + actual_dsp`,
so the frequency was off by 2 × the DSP residual: −3.7 to +8.5 kHz depending on
where the radio was tuned.

| File | Change |
|---|---|
| `src/security/wifi_frame_event.hpp` | New `CaptureRecord::stream_center_hz()` = `rf − dsp` (requested centre if the tune is unknown) |
| `src/drones/addon.hpp` | Native and legacy DJI observers use it (was `rf + dsp`) |
| `src/ml_inference.cpp` | `center_hz` sent to the ML worker uses it (was `rf + dsp`) |
| `src/shortrange/monitor.cpp` | Bluetooth/Zigbee decoder uses it |
| `src/scanner.cpp` | Coordinated derived LoRa channels: `actual_dsp_hz -= channel − step centre` (was `+=`), the matching sign for the derived channel's provenance |

The big picture first

Two systems run on the same captured IQ, independently, built at different times for different purposes. This matters everywhere below, because several parameters exist in two versions computed two different ways — most notably CFO (2.1 vs 8.2).

1

Detection stage

1.1 Preamble candidate & IQ polarity inverted_iq

The receiver doesn't assume the signal is right-side-up. LoRaWAN downlinks (and some other traffic) transmit with inverted IQ — the imaginary component negated, which flips a chirp's effective slope. Both polarities are tried on every capture.

How

The capture is chopped into non-overlapping N = 2^sf windows, each coarsely dechirped against the upchirp reference. A start index becomes a candidate only if the next min_preamble_symbols (default 6) windows all clear minimum_peak_ratio (0.5) and no consecutive pair drifts more than 1.5 bins. This search runs once on the IQ as captured, then again on its complex conjugate — that conjugation is the inversion.

1.2 SFD candidate

The point where the signal stops looking like more preamble and starts looking like the Start-Frame-Delimiter's downchirps.

How

From right after a confirmed preamble run, each subsequent window is dechirped against the downchirp reference. The first window whose downchirp ratio clears 0.5 and exceeds that same window's own already-computed upchirp ratio is the SFD candidate.

1.3 Alignment aligned

The single most important internal value — the resolved start of the SFD's first full downchirp. Almost every other parameter below is measured relative to this point.

How

Two fine (8× zero-padded) measurements bracket the SFD candidate: u (upchirp-matched, 4 symbols before it) and d (downchirp-matched, 1 symbol after it). Both slopes resolve timing/CFO up to an N/2 ambiguity; (d−u)/2 gives a position correction, tried at 3 half-symbol offsets × 3 symbol offsets — 9 candidates. The highest-scoring one, subject to three ratios all clearing 0.5, wins.

1.4 Preamble & SFD peak ratio preamble_peak_ratio · sfd_peak_ratio

Two confidence numbers shown directly in the GUI ("Preamble peak" / "SFD peak") — how cleanly the signal dechirped, on a 0–1 scale where ≈1.0 is a single dominant FFT bin. Lower values mean energy spread across many bins: noise, interference, or clipping — the same mechanism that made the 25 dB gain experiment fail earlier in this project's own history.

How

2

Timing & frequency

2.1 CFO — bins and Hz cfo_bins · cfo_hz

Carrier Frequency Offset: transmitter and receiver oscillators are never perfectly matched. Because a symbol's value is "which FFT bin has the peak," any CFO shifts every symbol's measured bin by the same constant amount. This is the decoder's own estimate — separate from the fingerprint's cfo_ppm (8.2).

How

Six preamble symbols well before aligned (offsets −8 through −3) are fine-dechirped and fit with an ordinary least-squares line: bin ≈ slope·j + intercept.

2.2 Drift — bins/symbol and Hz/symbol drift_bins_per_symbol · drift_hz_per_symbol

The oscillator mismatch isn't perfectly constant — it drifts slowly across a long packet. This is the rate of that drift, reused as-is from the same fit as CFO.

2.3 Capture offset (s) capture_offset_s

Where in this particular capture the packet's preamble was found — a coarse position marker, not a hardware timestamp.

3

Header-derived fields

All four fields come from one operation: dechirping the 8 symbols right after the SFD, correcting them (the mod-4-lattice variant of §2's drift model), Gray-decoding, diagonally deinterleaving at width sf−2, and FEC-decoding each codeword at the header's fixed CR=4 (4/8).

Declared payload length — nibbles 0–1, nib[0]×16 + nib[1].
Coding rate (CR) — nibble 2 bits 1–3. Displayed as 4/(4+cr): CR=3 shows as "4/7".
CRC-on flag — nibble 2, bit 0.
SF itself isn't calculated here — it's one of the (bandwidth, SF) hypotheses the scan loop already tries; a header only validates if the hypothesis matches the transmitter's real SF.

If sf−2 > 5, leftover nibbles beyond the first 5 (still coded at CR=4) are already the start of the payload — carried into §6 as a head start, not re-derived there.

Payload

6.1 FEC disagreements fec_disagreements

How many codewords — across both the header's 8 symbols and every payload block — needed any correction at all. Not a corrected-bit count, just "the received codeword wasn't already a perfect match."

How

6.2 Payload bytes payload

How

Each payload block (cr+4 symbols wide) is corrected, Gray-transformed — ÷4 for LDRO symbols, a −1 adjustment for ordinary symbols (genuinely different operations, not the same one) — deinterleaved, FEC-decoded, packed low-nibble-first into bytes (opposite of the header's high-nibble-first order), then dewhitened.

7

LoRaWAN structural fields

Gate before any of this runs: payload_complete && (!crc_on || crc_valid) — a candidate is only ever attempted against bytes that are either CRC-verified or declared to carry no CRC at all.

8

RF fingerprint

Runs independently of §§1–7, on its own alignment from lora::detect_burst() — a simpler, older detector, not the decoder's own aligned. It runs whether or not a header ever decodes: on hardware whose traffic never validates a header at all, this is still how it can be characterized.

8.2 CFO (ppm) fp_cfo_ppm

Not the same number as §2.1. The decoder's cfo_bins/cfo_hz never receives the absolute RF center frequency — only bandwidth. This calculation genuinely needs the carrier frequency (it's center_hz-relative by definition), uses a different estimator (Moose-style differential correlation), and a different alignment. Related, not identical, and not expected to match exactly.

How

8.3 IRR, IQ eps/phi, DC dBc/angle fp_irr_db · fp_iq_eps · fp_iq_phi_deg · fp_dc_dbc · fp_dc_ang_deg

Radio-hardware characteristics — image-rejection ratio, gain/phase imbalance between I and Q, and residual DC offset. These are the "stable core" identity features the persistent master list matches devices on (§9).

How — one 3×3 complex least-squares solve

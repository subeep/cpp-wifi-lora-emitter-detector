Emitter to Packet

The scanner runs two passes over the same radio, then hands anything it decodes to a third stage that tries to remember it. This is the full chain end to end — including the two mechanisms underneath it that are usually left as a black box: how a chirp collapses to a symbol, and how the spreading factor is actually decided rather than known.

01 — wideband sweep

Recognizing an emitter

Runs every cycle while the sub-GHz band is active. It never tries to decode anything — it just measures where energy is, how wide it is, and whether that shape looks like a known protocol.

The “power” column is not calibrated. psd_db = 10·log₁₀(max|FFT|² + 1e-15) — no division by FFT size, no window-energy correction, no per-Hz normalization. It reads relative to itself (that's all the threshold needs), not against a real reference like dBm.

03 — the physics inside step 4

How dechirping recovers a symbol

A LoRa symbol is not a tone, it's a chirp — a linear frequency sweep across the whole channel bandwidth, with the starting frequency encoding which of 2^SF symbol values was sent. Dechirping is the trick that turns that sweep back into something an FFT can read off directly.

1 · the reference chirp sweeps the full channel in one symbol φ(n) = 2π · ( n²/(2N) − n/2 ), n = 0…N−1  —  instantaneous frequency runs −BW/2 → +BW/2 linearly
2 · a symbol is that same chirp, frequency-shifted by its value sk[n] = upchirp[n] · ej2πkn/N  —  the shift is the symbol: k ∈ {0 … N−1}
3 · multiplying by the conjugate reference cancels the sweep v[n] = sk[n] · conj(upchirp[n]) = ej2πkn/N  —  a plain tone at frequency k/N, no sweep left
4 · an N-point FFT of an exact integer-periodic tone is one bin X[m] = Σn ej2πkn/N·e−j2πmn/N = N·δ(m−k)  —  argmax|X[m]| = k, read directly off the peak bin
What's cheap here is also what's crude here. The whole demodulator is critically sampled — N = 2^SF is simultaneously the samples-per-symbol, the FFT size, and the bin count, with no oversampling anywhere. The peak bin is an integer: CFO resolution is one bin (BW/N Hz) with no sub-bin interpolation in the decode path itself — that refinement exists only downstream, in the fingerprint extractor (§05), and never feeds back into decoding. The only quality gate is peak_mag / sum_mag > 0.5, checked at three places: locking 6 consecutive preamble symbols to the identical bin, measuring how many preamble symbols follow, and confirming the 2.25-symbol SFD (frame-sync downchirp) — whose own peak bin is discarded, so the code never disentangles a timing offset from a frequency offset.
04 — the search inside step 3

Deciding spreading factor and bandwidth

This is the answer to “how do we decode SF?” — and it's worth being precise, because we don't decode it. There is no SF estimator anywhere in the codebase. SF is a mandatory function argument, and the only way this project ever learns it is by trying every plausible value and seeing which one dechirps cleanly.

Once a hypothesis is picked, acceptance is a hard boolean per hypothesis — header checksum passes, or a bare preamble locks — with no scoring, no ranking, and no winner selection across the 24 attempts. The loop runs to completion every time, so one real burst can legitimately produce more than one logged row.

Why two different hypotheses can both look right

The dechirp match depends only on the reference chirp's sweep rate, not on SF and bandwidth individually. That rate is BW²/2^SF — and (SF, BW) and (SF+2, 2×BW) always produce the exact same number:

chirp rate is identical across the alias family rate = BW² / 2^SF  —  e.g. SF7/BW125k and SF9/BW250k both give 122.07 MHz/s exactly
11 / 11ambiguous captures in the live store share an identical chirp rate
0.81–1.00peak/sum ratio for the true hypothesis (simulated)

This is confirmed, not theoretical: re-simulating dechirp_analyze() exactly and sweeping it against every (BW, SF) hypothesis shows every rate-matched pair clears the preamble floor together. Cross-checking the live master-list store finds every one of the 11 timestamps where two device rows share an identical capture — all 11 — have exactly matching chirp rate, not a near miss. In the real example above (866.9 MHz, one TarangMini burst), SF7/BW125 scored sync_corr 0.821 and its SF9/BW250 alias scored 0.868 — the alias actually fit better, which is why arbitrating “pick the higher score” would not reliably resolve it either.

This aliasing explains duplicate rows in the packet table — it is not the main cause of device fragmentation below. Isolating to SF7 alone, with bandwidth and alias effects removed entirely, still splits 118 real readings from the one physical TarangMini into 23 separate device entries (§05). Two different degeneracies are stacked here: one in the PHY search, one in the identity matcher — and the identity matcher's is the larger of the two.
05 — after a “Detected” row

Packet to persistent identity

Every fingerprinted burst is checked against a permanent, on-disk device list — one .ndjson file per device under data/lora_master/, reloaded on startup, never auto-deleted. A successfully decoded packet never reaches this stage; only the fingerprinted “Detected” branch does.

If no device qualifies, a new one is created — display ID LORA-%04d — and is immediately matchable from its very first reading (unlike the session-only registry, which requires 3 readings first). There is no merge, split, or rename path anywhere in the class: once two entries exist for the same radio, nothing in the code ever puts them back together.

Every one of the four matched features drifts, on its own, well past its acceptance window over the life of one physical device — IQ ε the worst, by a wide margin. Because the four gates are ANDed, any single one of them tripping is enough to spawn a new device, and with four independent noisy features all exceeding tolerance, that happens often. It is not one bad gate; it's that a single raw reading is a poor proxy for a device that is this noisy from burst to burst, compared against a trailing median that is easily pulled off by the last few outliers.

where we're stuck

TarangMini's header still doesn't decode, and it's probably not a bug in our codec anymore. Every formula in the standards-compliant decoder — header checksum, Hamming FEC, diagonal interleaver, whitening — was transcribed and verified character-by-character against the reference LoRa-SDR implementation.

  • Working theory: TarangMini runs in implicit-header mode. TarangNet's own API never exposes a coding-rate setting — only spreading factor and bandwidth — which fits a proprietary stack that skips the standard explicit header entirely.
  • Tested directly: decoding raw payload blocks (no header assumed) across every coding-rate guess. Repeated real captures of the identical payload agreed with each other ~80% of the time bit-for-bit — proof the PHY lock is genuinely reading real signal — but matched the known plaintext 0% of the time, under every byte/nibble/bit ordering tried.
  • Newly found gap, worth ruling out: the standards codec has no low-data-rate-optimize (LDRO) path at all — a repo-wide search turns up zero hits. Real SX127x hardware mandates LDRO at SF11/SF12 on 125 kHz, which this decoder doesn't implement. That can't be the whole story (TarangMini fails to decode at SF7 too), but it is a confirmed fidelity gap against real hardware that hasn't been closed.
  • Current read: TarangNet likely encrypts or scrambles the payload above the PHY layer. That would make full payload recovery a protocol question, not a signal-processing one.
